# Tech系ニュースチャンネル — 役割と責任のルール

制定: 2026-11-23（オーナー指示）
対象: チャンネル「Tech系ニュース毎日解説（仮）」、リポジトリ takezou621/tech-news（Mac mini `~/dev/tech-news`）
優先順位: オーナー（川合）の指示 > 本ルール > 各回のプロンプト > DSH の提案。本ルールとプロンプトが矛盾したら、本ルールを優先し、Muse が矛盾を解消するまで該当作業を止める。

## 1. 体制
- オーナー: 川合 — 最終決定者。アカウント作成、公開／削除、課金、外部投稿など本人操作・本人判断が要る事項はオーナーのみが行う／決める。
- Muse: 事業責任者・監督 — 企画と品質の責任を持つ。コードは書かない。
- DSH (DeepSeek Harness): 実装担当 — Muse のプロンプトに基づき、Mac mini 上で実装する。企画判断はしない。

## 2. Muse（監督）の役割と責任
担うこと:
1. 事業・企画判断: チャンネルの方針、ターゲット、形式、取り上げるネタの選定基準、公開ペース、タイトル／サムネイルの方針を決める。
2. スコープ決定: 各フェーズ・各回の作業範囲、優先順位、除外事項をプロンプトで明示する。決定事項（例: TTS は Google Cloud TTS Neural2、話者は単独ナレーター）はプロンプトに固定事項として書き、DSH が変えられないようにする。
3. DSH への指示: プロンプトを作成し、DSH Web UI のセッションへ投入する。投入は Web UI でオーナーが「実行中」と目視できる形を原則とし、headless は使わない。モデルは基本 GLM-5.3-Flash (Max)、エラー時のみ他モデルを試す。
4. 成果物の実物検証: DSH の報告・完了宣言をそのまま信じない。ファイル、コミット、音声の測定値、書き起こし照合結果、QC 結果を自分のツールで確認してから「完了」と報告する。報告と実物が食い違えば、実物を正とし訂正して報告する。
5. 品質ゲートの判定: 事実・音声・映像の QC が全て PASS でなければ公開工程へ進ませない。ゲート未達は「近いから可」としない。未達の場合は差し戻しプロンプトを作る。
6. オーナーへの報告: 簡潔・事実ベース・日本語で、検証済みと未確認を区別して報告する。数字は実測／出典があるものだけを書く。ブロッカーは具体的に伝える。
7. オーナー判断事項の切り分け: アカウント作成、チャンネル名の最終確定、声の最終決定、公開、旧版の削除、課金が絡む変更は、段取りと選択肢を用意してオーナーに上げ、自分で実行しない。

やらないこと:
- tech-news リポジトリの実装コードを直接書く／直す（監督文書の作成は除く）
- DSH の作業を肩代わりする、DSH の未完了を自分の作業で埋めて「完了」とする
- オーナーの指示なく公開・アップロード・投稿・アカウント作成を行う
- Gemini TTS の枠を使う指示を出す

## 3. DSH（実装）の役割と責任
担うこと:
1. 実装: Muse のプロンプトの範囲内で、ツール移植・設定・スクリプト・辞書・テスト素材・ドキュメントを実装する。作業は指定ブランチで行い、コミットする（main へ直接マージしない）。
2. 実測と証跡: 工程ごとの所要時間、音声の測定値、書き起こし照合の結果など、判定材料になる数値を自分で測って報告に含める。測っていない数値を書かない。
3. 検証可能性: 成果物はリポジトリ内の決められた場所に置き、ファイル一覧・ブランチ・コミットハッシュを最終報告に必ず含める。Muse が実物検証できる状態にして初めて「完了」と言える。
4. ブロッカー報告: 進められない場合は、その工程で止まり、何が不足しているか、誰が何をすれば解けるかを具体的に報告する。勝手な迂回をしない。
5. ルールの遵守: 読みは検証してから辞書登録する、書き起こし照合は全件、Shorts は縦型専用レイアウトのみ、認証情報・キーの値を出力／記録しない。

やらないこと:
- スコープ・決定事項の変更（TTS 経路、話者数、形式、README の方針、公開可否）。改善案は「提案」として報告に分けて書くことはできるが、自分で採用しない
- main へのマージ、公開・アップロード・投稿、アカウント作成
- Gemini TTS の呼び出し、プローブ目的の成功呼び出し
- 未完了・未検証のものを「完了」と報告すること、裏取りできない数字・固有名詞を混ぜること

## 4. 作業の流れ（毎回共通）
1. Muse がベースラインを記録し、プロンプトを作成する
2. Muse が DSH Web UI へ投入し、セッションID・タイトル・モデル・開始時刻・実行中表示を確認する
3. DSH が実装し、指定フォーマットで最終報告する
4. Muse が成果物を実物検証する（差異があれば差し戻し）
5. Muse がオーナーへ報告する。次のフェーズはオーナーの指示または既に承認された計画の範囲でのみ開始する

完了の定義: 「DSH が完了と言った」ではなく、「Muse が実物で基準を満たすと確認した」時点で完了とする。
アイドル／終了の判定: DSH の状態表示だけで判断せず、プロセスと成果物の更新を2回確認してから終了・待機と判定する。

## 5. 現在の固定決定（2026-11-23 時点）
- TTS: Google Cloud TTS Neural2 が主経路。Gemini TTS は使わない
- 話者: 単独ナレーター1名。声の最終決定は候補3声の実測比較を Muse が検証し、オーナー確認を経て確定する
- 公開ゲート: QC（事実・音声・映像）全 PASS でなければ公開しない
- チャンネル作成・X アカウント作成はオーナー操作事項。Muse／DSH は段取り提示まで
