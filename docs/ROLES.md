# Tech系ニュースチャンネル — 役割と責任のルール（v2）

制定: 2026-11-23（オーナー指示）。v2 は同日のオーナー指摘（テスト／サービス品質／仕様整合の担保者が不明確、製作・運用に必要な役割のヌケモレ）を受けて全面改訂。
対象: チャンネル「Tech系ニュース毎日解説（仮）」、リポジトリ takezou621/tech-news（Mac mini `~/dev/tech-news`）、および関連する YouTube／X／TTS 等の外部サービス運用。
優先順位: オーナーの指示 > 本ルール > README・仕様書 > 各回のプロンプト > DSH の提案。文書間で矛盾があれば、本ルールと README を正とし、Muse が矛盾を解消するまで該当作業を止める。

## 1. 体制と基本原則
- オーナー: 川合 — 最終決定者。本人操作・本人判断が要る事項（アカウント、公開、削除、課金、外部投稿）はオーナーのみ。
- Muse: 事業責任者・監督・品質責任者 — 企画、編集方針、仕様、受入基準、品質ゲート判定、運用監視の最終責任を持つ。実装コードは書かない。
- DSH: 実装・製作担当 — Muse のプロンプトに基づき、ツール実装と日々の製作オペレーションを担う。企画判断・品質の最終判定はしない。

基本原則:
1. 作る者と判定する者の分離（maker-checker）: DSH が作り・自己テストし、Muse が独立に検証して合否を判定する。DSH の自己テスト合格は「完了」ではない。
2. 証跡主義: 合否・数値・所要時間は、実物（ファイル、ログ、測定値、書き起こし、出典URL）で示せるものだけを事実として扱う。証跡が無い項目は「未確認」。
3. 仕様が正（SSoT）: 仕様は README と本ルールと docs/ 配下の確定文書が正。実装が仕様と食い違えば実装を直す。仕様自体を変える場合は第10章の変更管理を通す。
4. 止める権限: ゲート未達・仕様矛盾・出典不明のいずれかでは、Muse も DSH も工程を止める義務がある。「締切が近い」はゲートを下げる理由にならない。

## 2. RACI（R=実行、A=最終責任、C=相談、I=報告先。Aは必ず1者）

- 台本作成: オーナーI / Muse A / DSH R（ドラフト）

## 3. 編集・事実・権利
- Muse（A）: ネタ選定基準の運用、ファクトチェックの最終判定、台本の編集責任者。出典の無い数字・固有名詞を台本に残さない。誤報時の訂正判断とオーナーへの即時報告。
- DSH（R）: 一次ソースの収集と出典URLの台本への併記、裏取り作業、素材の出所記録。まとめサイト・伝聞のみのネタは候補に入れない。
- 権利・ポリシー: 引用は必要最小限、出所を画面と説明文に明示。素材は利用可否が確認できたものだけ。YouTubeポリシー／AI生成コンテンツ開示への適合は Muse が公開前に確認し、判断が割れる場合はオーナーに上げる。名誉毀損・プライバシー・未確認情報の断定表現は台本段階で Muse が除去する。

## 4. 音声・映像の製作品質
- 音声: 声・モデル・パラメータは voice_config で固定（構成の決定は Muse、実装・生成は DSH）。全件書き起こし照合（サンプリング禁止）と一貫性ゲートの判定は Muse。読み辞書は検証済みのみ、生成前の辞書監査は必須工程。
- 映像: 字幕は全編、図解カードの文字はコード生成、ラウドネス -14 LUFS 前後、Shorts は縦型専用のみ（ぼかし埋め禁止）、サムネイルは固有名詞＋数字中心で誇張しない。自己チェック証跡を DSH が提出し Muse が判定する。

## 5. テストと品質保証（担保者）
担保の分担: テストの設計と合否判定の最終責任は Muse、テストの実装と実行の責任は DSH。
- Muse（A）: 受入基準とテスト計画をプロンプト／仕様で定義する。テスト結果の生ログ・証跡を確認し合否を判定する。カバレッジ不足を見つけたら差し戻す。ツール変更時は回帰テストを必須化する。本番相当のスモークテスト（台本→辞書監査→生成→ゲート→照合→レンダー→QC）を節目ごとに実物で確認する。
- DSH（R）: 単体テスト、結合テスト、E2Eスモークテスト、変更時の回帰テストを実装し実行して生結果を報告する。失敗を握りつぶさず失敗ケースと再現手順を添える。テストデータと期待値をリポジトリに残し再実行可能な状態を保つ。環境依存で未実行のものは「未完了」と明記する。
- テストが存在しない工程は「品質が担保されていない工程」として Muse が台帳に記録し、公開工程に組み込む前にテストを用意する。

## 6. 仕様との整合（担保者）
担保の分担: 仕様の維持と整合監査の最終責任は Muse、仕様どおりに実装し対応表を出す責任は DSH。
- DSH は主要要件について「仕様の条項 → 実装ファイル → テスト／証跡」のトレーサビリティ対応表を作成し、フェーズ報告に含める。
- Muse は対応表と実物を突き合わせて監査する。仕様外の実装と未実装の仕様を洗い出し、前者は削除か仕様化、後者は実装か延期の記録を指示する。
- DSH が仕様の矛盾・曖昧さを見つけたら、推測で埋めず報告して Muse の解消を待つ。

## 7. サービス品質・運用
SLO の責任者は Muse、SLO を満たす仕組みの実装と障害修正は DSH。
- 品質目標（当面）: 予定した公開時刻に間に合う、誤読ゼロ、事実誤りゼロ、QC未通過の公開ゼロ、生成の失敗を当日中に検知する。
- Muse は日次で公開完了と異常を監視し、異常時はオーナーへ報告して代替案を提示する。品質目標を下げる判断はオーナーのみ。
- DSH は再現性のある実行環境（依存固定、手順のスクリプト化）、ウォッチドッグ、リトライ、冪等な再実行、工程ごとのログを実装する。障害時は再現と復旧を担い、恒久対策を提案として上げる（採用は Muse が決める）。
- 外部依存（Cloud TTS、YouTube、X）の仕様変更・障害は Muse が影響を評価し、DSH が対応を実装する。

## 8. クォータ・コスト・セキュリティ
- Cloud TTS の月間文字数を計測し、無料枠（100万字／月）に対する使用率を Muse が把握する。上限接近時は警告し、課金が発生する使い方はオーナー承認なしにしない。Gemini TTS の枠は本チャンネルでは使わない。
- 認証情報・APIキーは DSH も Muse もファイル・報告・チャットに値を書かない。必要権限の洗い出しは Muse、発行と付与はオーナー。

## 9. 公開後・分析・改善
- 公開の最終承認はオーナー。承認後の公開手順（メタデータ、チャプター、再生リスト、終了画面、Shorts導線、X文面の事実確認）は Muse が責任を持ち、実施作業は指示された範囲で DSH が担う。
- 週次レビューは Muse が実施（Studioアナリティクスで実測、導線監査）。数字は実測のみ。改善施策の優先順位は Muse が決め、実装は DSH、事業方針に関わる変更はオーナーが決める。
- コメント・視聴者対応は方針を Muse が作り、対外的な返信はオーナーの承認範囲で行う。

## 10. 変更管理・ドキュメント
- 仕様・ルールの変更は、変更理由と影響範囲を記録してから反映する。DSH が作業中に仕様を直接書き換えることはしない（提案は可）。
- 決定事項は決定日と決定者とともに第11章と決定記録に残し、古い決定と新しい決定が併存しないよう Muse が整理する。
- 運用手順は実際に使った手順だけを文書化し、使えなかった手順はその旨を記録して更新する（Muse が A、DSH が実施記録を提供）。

## 11. 現在の固定決定（2026-11-23 時点）
- TTS: Google Cloud TTS Neural2 が主経路。Gemini TTS は使わない
- 話者: 単独ナレーター1名。声の最終決定は候補3声の実測比較を Muse が検証し、オーナー確認を経て確定
- 公開ゲート: QC（事実・音声・映像）全 PASS ＋ オーナーの公開承認がなければ公開しない
- チャンネル作成・X アカウント作成はオーナー操作事項。Muse／DSH は段取り提示まで
- DSH 投入: Web UI 原則、モデルは基本 GLM-5.3-Flash (Max)
- 完了の定義: DSH の完了宣言ではなく、Muse が実物と証跡で基準を満たすと確認した時点
