# tech-news — Tech系ニュース毎日解説チャンネル

Tech系ニュースを **毎日・約5分・日本語** で解説する YouTube チャンネルの企画と製作フローを管理するリポジトリ。

- ターゲット: エンジニア、技術系経営者
- 形式: 1日1本、約5分（ナレーション約1,600字が目安）
- 方針: 一次情報（公式発表・リリースノート・論文・公式ブログ）に基づく解説。数字と固有名詞は必ず出典で裏取りし、創作しない

この README は、先行チャンネル「アニメ日本史ラボ」で確立した動画製作フローを、本チャンネル向けに整理し直したものです。

---

## 1日のタイムライン（案）

| 時刻 (JST) | 工程 |
|---|---|
| 06:00 | ネタ収集（前日21:00〜当日朝の発表が対象） |
| 06:30 | 選定（3〜5件）と台本作成、ファクトチェック |
| 07:00 | 音声生成 → 書き起こし照合 |
| 07:30 | 編集・レンダー → QC |
| 08:00 | 公開、Shorts 切り出し、X 告知 |

※ 公開時刻は案。通勤時間帯（7〜8時）か昼休み（12時）かは、初期の視聴データで見直す。

## 製作フロー

### 0. ネタ収集・選定
- 情報源は一次ソースを優先する: 企業公式ブログ・プレスリリース、GitHub のリリース/チェンジログ、公式ドキュメント、論文（arXiv 等）、標準化団体の発表
- まとめサイトや SNS の伝聞だけで取り上げない。元発表に当たれないネタは見送る
- 選定基準: (1) 実務への影響が大きい、(2) 技術的な中身がある、(3) その日のうちに伝える価値がある

### 1. ファクトチェック
- 数字・日付・バージョン・価格・固有名詞は、一次ソースで裏取りしてから台本に入れる
- 台本には各ネタの出典 URL を併記し、公開時の説明文にも転記する
- 裏取りできない数値は「未確認」と明示するか、使わない

### 2. 台本
構成テンプレート（1ネタあたり）:
1. ヘッドライン（何が起きたか、1文）
2. 詳細（何がどう変わったか）
3. 技術的な意味（なぜ重要か、仕組みの要点）
4. 実務への影響（エンジニア/経営者として何をすべきか）

- 全体で約1,600字（約5分）。1ネタ 300〜500字 × 3〜5件
- 冒頭15秒でその日の最重要ネタを提示する

### 3. 読み辞書（発音辞書）
- 製品名・企業名・技術用語の読みは、**検証してから** 辞書に登録する（例: NVIDIA、Kubernetes、Gemini 等の英語固有名詞、日本語の難読語）
- 辞書に無い語は生成前に洗い出し、読みを確認してから追加する。推測の読みで生成しない
- 先行チャンネルの教訓: 辞書の誤りはそのまま音声の誤りになる（例:「乙巳の変」を誤読して修正版を再アップした）。生成前の辞書監査を工程として固定する

### 4. 音声生成（TTS）
- モデル・声・スタイル指示・生成パラメータは設定ファイル（voice_config 相当）で**固定**し、話者ごとの声の同一性を仕組みで担保する（都度調整しない）
- 生成後は音声一貫性ゲート（ピッチ/テンポの外れ値を検出）を通す
- TTS 呼び出しにはウォッチドッグ（ハングしたら自動で切って再試行）を付ける
- プローブ目的の成功呼び出しはしない（枠を消費するため）

### 5. 全文書き起こし照合
- 生成した全音声を Whisper 等で書き起こし、台本と**全件**照合する（サンプリング確認は禁止）
- 誤読・欠落・重複があれば該当部分だけ再生成する

### 6. 編集・レンダー
- 字幕は全編に付ける。図解カード（アーキテクチャ図、比較表、数字の強調）はコード生成で正確な文字を出す
- 出典は画面内にも小さく表示する
- ラウドネスは YouTube 基準（-14 LUFS 前後）にそろえる

### 7. QC（公開ゲート）
以下の3点がすべて PASS でなければ公開しない:
- 事実: 台本の数字・固有名詞が出典と一致している
- 音声: 書き起こし照合で誤読ゼロ、声の一貫性ゲート PASS
- 映像: 字幕の誤字・はみ出し、カード表示タイミングのずれがない

### 8. サムネイル
- 文字中心（ネタの固有名詞＋数字を大きく）。クリックベイトな誇張はしない

### 9. 公開
- タイトル: 最重要ネタを軸に、固有名詞と具体性で構成する
- 説明文: 各ネタの出典リンク、チャプター（タイムスタンプ）、シリーズ再生リストへの導線
- 公開後に再生リストへ話数（日付）順に追加し、終了画面（再生リスト＋チャンネル登録）を設定する

### 10. Shorts
- 本編から1ネタを切り出し、**縦型専用レイアウト**（1080×1920）で再構成する。横型映像を中央に置いて上下をぼかす方式は使わない
- Short の説明文に本編 URL を入れ、本編への導線にする

### 11. X 告知
- 公開に合わせて告知ポスト（本編リンク付き）。文面の事実は台本準拠のみとし、煽り文句や数字の創作はしない

### 12. 週次レビュー
- YouTube Studio アナリティクスで登録者数・再生数・Shorts 別の再生数を実測し、前週比と一緒に記録する（GA4 は YouTube 内の導線を測れないため使わない）
- Shorts→本編の導線（説明文リンク、再生リスト、終了画面）を監査し、欠けがあればその場で直す

## 訂正ポリシー
- 公開後に誤りが見つかった場合: 該当部分を直した修正版を再アップロードし、旧版は非公開化する（削除はオーナー判断）
- YouTube は動画ファイルの差し替えができないため、再アップ＋差し替えが前提の手順になる

## 技術メモ・流用元
- 製作基盤は先行チャンネル `anime_japanese_history`（Mac mini 上）の `tools/audio/` 一式（統一音声生成、一貫性ゲート、読み辞書、レンダー/QC）を流用する
- **TTS 枠の注意**: Gemini TTS（プロジェクト muse-gemini）は 50 リクエスト/日で、アニメ側の日次生成と共有している。本チャンネルが毎日使うと枠を取り合うため、以下のいずれかを初回製作前に決める:
  - 推奨: Google Cloud TTS（Neural2、無料枠 100万字/月）の併用 — 5分/日 ≒ 月約5万字で無料枠に十分収まる（eng-listening で実績あり）
  - 別 Gemini プロジェクトを用意して枠を分離する

## リポジトリ構成（案）

```
tech-news/
  README.md            # 本書
  content/
    episodes/
      YYYY-MM-DD/
        script.json    # 台本（出典URL併記）
        sources.md     # 収集した一次ソースのメモ
  tools/               # 生成・編集ツール（流用元から移植）
  audio/               # 生成音声（話ごと）
  video/               # レンダー成果物とQC結果
  youtube/             # 公開メタデータ（タイトル・説明文・サムネイル）
```
